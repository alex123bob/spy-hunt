# Accounts (Guest-First Registration and Login) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A guest can register (email + password) without losing their bots, streak or history, log in on another device to see the same data, log out of just that device, and get three soft, dismissible nudges toward registering — all without ever blocking guest play.

**Architecture:** Backend: a `sessions` table generalizes the existing single-token-per-guest model to many tokens per `player_id`, four new routes (`/register`, `/login`, `/logout`, `/me`) sit beside the untouched `require_guest`/`g.player_id` plumbing, and the daily streak moves from client `localStorage` to a read computed from the already-written `puzzle_results` table. Frontend: a shared top-bar layout (language picker + account link) wraps every screen, a modal handles register/login, a small nudge-banner component reads three independent triggers, and the local streak module is deleted in favor of fields the daily endpoints now return.

**Tech Stack:** Python 3 / Flask / SQLite / pytest with `fake_llm`; React 19 / TypeScript / vitest / Playwright. No new dependency: password hashing uses `werkzeug.security` (already present via Flask).

**Spec:** `docs/superpowers/specs/2026-11-11-accounts-design.md` (in `spy-hunt`, this repo). Read it first; section numbers below refer to it.

## Global Constraints

- No new backend dependency; password hashing uses `werkzeug.security.generate_password_hash` / `check_password_hash`.
- `player_id` never changes on register or login; every table and rate-limit bucket keyed on it (`custom_bots.owner_player_id`, `remixes`, `guest_recent_pairs`, `players.player_id`, `rooms.host_player_id`, `guest:{player_id}` buckets) is untouched by this slice.
- Existing guest tokens issued before the migration keep working with no forced re-login.
- The `Authorization: Bearer player_id.token` request shape is unchanged; only how tokens are minted/validated changes (lookup moves from `guests.token_hash` to `sessions`).
- Minimum password length: 8 characters, server-side only. Email is lowercased and trimmed before storage/lookup.
- zh-Hans and en copy for every new label.
- Rate limits: `register`/`logout` use `action` (guest-scoped, existing); `me`/`daily/streak` use `read` (guest-scoped, existing); `login` is a new IP-scoped limit, suggested 20/min, since it runs before any guest token exists.
- Streak milestone threshold and return-visit count: named constants, suggested value 3 for both.
- Code comments only where behaviour is not obvious.

## Review Focus

1. **Login from a second device does not evict the first.** Two valid tokens for the same `player_id` both keep working after a login; `POST /logout` on one device removes only that device's token row, and the other device's token is still valid after. Task A2.
2. **Streak correctness at the removed-client-state boundary.** A player who solved yesterday and today has `streak` continue correctly server-side, even though no client migration/backfill runs; a player who solved today but not yesterday restarts at 1; a player who has never played gets `streak: 0, best: 0` with no row at all (not a crash on an empty `puzzle_results` scan). Task A3.
3. **Re-registering an already-registered guest is rejected, not silently overwritten.** `POST /register` on a `player_id` that already has an email returns `409 conflict` rather than replacing the stored credentials. Task A1.
4. **Old guest tokens issued before this slice's migration keep authenticating.** A token whose hash exists only in the legacy `guests.token_hash` column (never backfilled, if the migration were skipped) must not silently 401 — the migration step itself, run via `init_db()`, is what the test must prove, not just the lookup code. Task A1.
5. **Nudge precedence and dismissal are independent per trigger.** All three nudge conditions true at once still shows only one banner (streak/win beat return-visit); dismissing the streak banner this session does not suppress a later win banner; an account already existing suppresses all three regardless of any trigger condition. Task F3.

**Interfaces:**
- Produces (schema, `db.py` `SCHEMA`): `sessions(token_hash TEXT PRIMARY KEY, player_id TEXT, created_at INTEGER)`; `guests` gains `email TEXT`, `password_hash TEXT` via the existing idempotent `ALTER TABLE` loop in `init_db()`; a partial unique index `CREATE UNIQUE INDEX IF NOT EXISTS idx_guests_email ON guests(email) WHERE email IS NOT NULL`.

## Task A3: Daily streak moves server-side

**Files:**

**Interfaces:**
- Consumes: `puzzle_results` table (unchanged schema), `utc_day()`, `check_day()`, `_tx()`, `get_conn` from `db.py`.
- Produces (`db.py` `SCHEMA`): index `CREATE INDEX IF NOT EXISTS idx_puzzle_results_player ON puzzle_results(player_id, day)`.
- Produces (`puzzles.py`): `streak_for(player_id: str, today: Optional[str] = None) -> Dict[str, Any]` returning `{"streak": int, "best": int, "played_today": bool}`. Reads every `puzzle_results` row for `player_id` with `stage='done'` ordered by `day` ascending; walks the ordered `(day, solved)` pairs computing the same semantics as the removed `streak.ts` (`loadStreak`/`recordResult`/`currentStreak`): a run of consecutive calendar days (by UTC date string, no gaps) with `solved=1` ending on a given day continues that day's streak at 1 + previous, any `solved=0` day or a gap resets the run to 0 starting fresh (not counted) from the next solved day; `best` is the maximum run length ever seen across the whole history; the returned `streak` is the run ending at `today` if it has a `done` row today, else the run ending at `today - 1` if yesterday was the end of a live run, else `0` (mirrors old `currentStreak`'s "still alive" rule — a streak survives exactly one missed/not-yet-played day before showing as 0). `played_today` is `True` iff a row `(today, player_id)` exists with `stage='done'`. A `player_id` with zero `done` rows returns `{"streak": 0, "best": 0, "played_today": False}` with no error.
- Produces (`get_today`, `result`): both existing functions gain `streak`/`best`/`played_today` in their returned dict, merged in via `streak_for(player_id, day)` (no change to their existing keys).
- Produces (route, under `/api/spy-hunt`): `GET /daily/streak` — `@ratelimits.limit("flood")`, `@auth.require_guest`, `@ratelimits.limit("read")`, returns `jsonify(puzzles.streak_for(g.player_id))`.
